Review collection playbook

The implementation contract for native Shopify review prompts and contact capture.

New app runbook
Implementation 1. Understand the flow 2. Choose success 3. Capture contacts 4. Report usage 5. Open the prompt 6. Report outcome 7. Configure Mantle 8. Test end to end Definition of Done

Architecture

1. Understand the trusted flow

  1. The embedded app authenticates the Shopify session and captures the shop plus current staff member.
  2. A persisted business action succeeds and the app reports one idempotent usage event to Mantle.
  3. Mantle applies the shared policy and may return a short-lived decision ID.
  4. The app claims that decision in its own authenticated backend, then calls shopify.reviews.request() in the embedded frontend.
  5. The app reports Shopify's exact result to Mantle. A displayed modal is not proof that a public review was posted.
Trust boundary. The browser never receives MANTLE_USAGE_TOKEN. Shopify identity is validated by the app; policy and history belong to Mantle.

Product rule

2. Choose a real success event

Ask after the merchant has received value, not after login, installation, navigation, a lookup, or a failed action. The event must originate from committed application state.

Use a stable event ID derived from the saved record, for example book-import:<database-id>:success. Retries must reuse it.

Every authenticated session

3. Capture shop and staff contacts

Use Shopify token exchange for the staff identity. Store staff by Shopify user ID, not email, so multiple employees remain separate. Only send an email when Shopify marks it verified.

Read the shop plan through Admin GraphQL and send Shopify's authoritative development-store flag:

query ShopContactContext {
  shop {
    id
    email
    contactEmail
    plan { partnerDevelopment publicDisplayName }
  }
}
POST /ingest/contacts/<app-slug>
X-Usage-Token: <MANTLE_USAGE_TOKEN>

{
  "shop_gid": "gid://shopify/Shop/123",
  "shop_domain": "store.myshopify.com",
  "kind": "shop",
  "email": "owner@example.com",
  "email_verified": true,
  "partner_development": false,
  "seen_at": "2026-08-13T10:00:00Z"
}
Development stores. When shop.plan.partnerDevelopment is true, Mantle never issues a review decision. Shopify can show a test modal there, but the store cannot publish a review.

Server to server

4. Report the successful action

POST /ingest/usage/<app-slug>
X-Usage-Token: <MANTLE_USAGE_TOKEN>

{
  "events": [{
    "shop_gid": "gid://shopify/Shop/123",
    "event_id": "book-import:481:success",
    "event_type": "book_import_succeeded",
    "occurred_at": "2026-08-13T10:04:00Z",
    "properties": {}
  }]
}

Retry network and 5xx failures with bounded backoff. A duplicate event is safe. Never make the merchant's successful workflow fail because Mantle is unavailable.

{
  "stored": 1,
  "review_prompt": {
    "decision_id": "opaque-single-use-value",
    "expires_at": "2026-08-13T10:19:00Z"
  }
}

Embedded frontend

5. Open Shopify's native prompt once

Persist the returned decision in the app database. Expose it only through an authenticated app endpoint and atomically claim it before opening the modal. On embedded desktop, call:

const result = await window.shopify.reviews.request()

Do not build a custom rating modal, offer an incentive, send review-request emails, or block functionality. The decision expires after 15 minutes and is single use.

Exact Shopify result

POST /ingest/review-outcomes/<app-slug>
X-Usage-Token: <MANTLE_USAGE_TOKEN>

{
  "decision_id": "opaque-single-use-value",
  "success": false,
  "code": "cancelled",
  "message": "Merchant closed the dialog"
}

Mantle management

7. Configure only after telemetry works

  1. Add the usage event to the app's allowlist and set its usage-token ENV name.
  2. Deploy the app with contact, usage, and outcome reporting while review prompting remains disabled.
  3. Verify contacts and success events in Mantle.
  4. Set the success event, minimum event count, minimum install age, cancellation retry, and annual cap.
  5. Enable native prompts last.

Verification

8. Test end to end

  1. Use a development store to verify rendering only; expect Shopify's “testing purposes only” notice and no publishable review.
  2. Confirm Mantle received partner_development=true and does not issue further decisions for that store.
  3. For policy verification, create a short-lived test decision explicitly rather than weakening production rules.
  4. Trigger the real committed success path and verify exactly one local decision is stored.
  5. Reload and navigate: the decision must not open twice.
  6. Close the modal and verify the exact Shopify code, next eligible date, and merchant history in Mantle.
  7. Test Mantle downtime: the app workflow must still succeed.
  8. Redact the shop and confirm contacts disappear while aggregate decision history remains without response messages.

Working example

Book Importer reference files

  • app/jobs/shopify/after_authenticate_job.rb reads shop contact and development status.
  • app/services/mantle/contact_capture.rb derives trusted staff identity from Shopify token exchange.
  • app/jobs/mantle/report_usage_event_job.rb reports the committed success event.
  • app/controllers/api/review_prompts_controller.rb claims decisions and reports outcomes.
  • app/frontend/hooks/useReviewPrompt.ts calls the native Reviews API once.
  • app/models/book_import.rb emits only after a successful persisted state transition.

Release gate

Definition of Done

  • Success event represents delivered merchant value and has a stable ID.
  • Shop and every staff user are captured from authenticated Shopify data.
  • partnerDevelopment is reported and confirmed development stores are excluded.
  • All Mantle calls are server-side, authenticated, bounded, retryable, and non-blocking.
  • A decision is persisted and atomically claimed before the frontend opens it.
  • The native Shopify result is reported exactly; “shown” is not called a posted review.
  • Duplicate events, reloads, multiple staff sessions, cancellation, cooldown, mobile, and downtime are tested.
  • Prompting is enabled only after contact and usage telemetry are visible in production.
